# In a root npm workspace the frontend's tools live in ./node_modules, and every "frontend/node_modules" check silently skips

**Key lesson:** With `workspaces: ["frontend"]` at the repo root, `npm ci` hoists everything to `./node_modules` (only Vite's cache ever appears in `frontend/node_modules`), so gate on the root `node_modules/` and make `make lint`/`test` fail, not skip, when `frontend/` exists without it; and run `next typegen` before `tsc --noEmit`, or `PageProps`/`LayoutProps` don't exist.

- **Date:** 2026-09-27 · **Task:** task-039 · **Area:** frontend
- **Artifacts:** `Makefile` (`frontend-deps`), `.claude/hooks/autofix.sh`, `.github/workflows/{lint,test}.yml`, `frontend/next.config.ts`, `frontend/src/lib/search-state.ts`

## What we set out to do
Stand up the Next.js skeleton as an npm workspace member, wire prettier/eslint/tsc/vitest into `make lint`,
autofix and CI, and write the URL↔state reducer.

## What we learned
- **Hoisting moved every tool.** After `npm install` at the root, `frontend/node_modules` did not exist
  (later only `.vite/` appeared there), yet the Makefile, `autofix.sh` and its case-table row all tested
  `frontend/node_modules`. The old `make lint` would have passed without running a single frontend check.
  The hook now tests `$root/node_modules` (mutant "autofix looks for node_modules in frontend/", killed),
  and `make fmt/lint/test` depend on `frontend-deps`, which fails with "run make sync" instead of skipping.
- **`npx --no-install` from `frontend/` finds the hoisted bins** (`npx --no-install next --version` →
  16.3.6), so the Makefile can keep `cd frontend && npx --no-install …`.
- **`tsc --noEmit` alone fails on Next 16 pages** (`TS2304: Cannot find name 'PageProps'`): the route-type
  globals are generated into `.next/types` by `next typegen`/`next build`. `make lint` and the `typecheck`
  script run `next typegen` first; `next-env.d.ts` is regenerated by it, so it is gitignored.
- **Standalone output follows the tracing root.** With deps hoisted, `outputFileTracingRoot` (and
  `turbopack.root`) must be the workspace root; the server then lands at
  `.next/standalone/frontend/server.js`, not `.next/standalone/server.js`, and `.next/static` must be
  copied beside it (`npm start` does; the Docker image must too).
- **CI's schema-freshness step would have fired on the skeleton.** It was gated on
  `frontend/package.json` existing and ran `op openapi` + `npm run gen:api`, neither of which exists before
  TASK-040/035. It is now gated on `frontend/src/api/schema.ts`.
- **`create-next-app` 16 writes `AGENTS.md`/`CLAUDE.md` into the app** (and `next dev` re-adds the block).
  They were removed; the repo's own CLAUDE.md governs.
- `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` compile cleanly with Next 16, next-themes
  and the shadcn `cn` helper.

## Dead ends — don't repeat these
- npm 10.8 (Node 20) failed the first workspace install with `Cannot read properties of null (reading
  'edgesOut')`; npm 11 installed it. The lockfile is v3 and `npm ci` on CI's Node 22 reads it.
- `next/font/google` (the scaffold default) fetches fonts at build time; the Docker build must work
  offline, so the skeleton uses system font stacks.

## Decisions (and what would change them)
- The reducer takes a server-supplied `FilterClause {source, span, values}` and splices `q`; it never
  parses. It throws on a stale clause, an emptied field or a non-identifier value rather than no-op. If
  `/parse` grows a per-field clause summary (TASK-078), the type is derived from the schema instead.
- `mode` is part of the result-set key with `q` (it changes how `q` is read); `sort`/`page` are view state.
- Node 22 via `.nvmrc`, because Vitest 5 requires ≥ 22.12 and CI already used 22.

## Addendum — 2026-09-27 (review round 1)
- **Splicing text into `q` needs the server lexer's view of the text next to the splice.** `foo\` parses,
  but `(foo\) AND track:(…)` is `PARSE_UNBALANCED_PAREN`, because a backslash escapes the next non-space
  character (evidence: `uv run python -c 'parse("(foo\\) AND track:main")'`; an even run of backslashes is
  fine). The reducer now refuses a `q` ending in an odd run, and the goldens live in one JSON file that both
  vitest and a backend contract test read (`frontend/src/lib/wrap-golden.json`,
  `backend/tests/contract/test_frontend_wrap_golden.py`), so the two sides can't drift.
- **A clause handed to the reducer must say what it is.** Without `field` and polarity, "add main" to
  `-track:workshop` produced `-track:(workshop OR main)`, silently flipping the query. Without `mode`, a
  clause fetched before `setMode` still applied. `FilterClause` now carries `field`, `negated: false` and
  `mode`, and each is checked (TASK-078 AC #4).
- A toggle's accessible name must contain its visible text (WCAG 2.5.3): "Light" shown with the name
  "Switch to dark theme" fails. Stable text "Dark theme" plus `aria-pressed`, tested with Testing Library
  under jsdom (which needs a `matchMedia` stub for next-themes).

## Addendum — 2026-10-03: exact workspace pins and lock metadata

The dependency update's functional CI passed with Vitest resolved to 5.0.3 even though the frontend
manifest pinned exactly `5.0.3` and the root lockfile's frontend workspace recorded `^5.0.3`.
Successful installation proves the resolved version works, but not that the workspace metadata
records the intended exact pin. Correct that single metadata field without regenerating unrelated
platform-specific optional packages, and keep the as-built frontend stack description synchronized
with its manifest. PR #100 updates Next/eslint-config-next to 16.3.7 and Vitest to 5.0.3;
`docs/specs/05-frontend.md` now also corrects the inherited stale React description to 19.3.0.

## Addendum — 2026-10-07: Dependabot's npm updater can write a caret into the workspace entry (twice so far)

- **The caret.** PR #124 (Next and eslint-config-next 16.3.7 → 16.3.8) recorded
  `"eslint-config-next": "^16.3.8"` in the lockfile's `packages["frontend"]`, while `frontend/package.json` pins
  `16.3.8` exactly. In PR #100 the same updater wrote `^5.0.3` for Vitest and kept Next exact; here it kept Next,
  TanStack Query and `@types/node` exact. So it is one entry per bump, on a different package each time, and it
  comes from Dependabot, not from a hand edit. `npm ci --ignore-scripts` accepts the drifted lock and leaves it
  unchanged, so no CI job notices. Each npm Dependabot PR therefore gets a check before review: every
  `dependencies`/`devDependencies` entry in `frontend/package.json` equals `packages["frontend"]` in
  `package-lock.json` (the same strings, no extra names), and a drifted field is corrected by hand.
- **Next 16.3.8 is a security release.** Its notes list seven advisories, among them a server-side request
  forgery in Image Optimization (GHSA-cjq9-62q9-8jv4; `/_next/image` is on in the standalone build) and cache
  poisoning of SSG/ISR pages (GHSA-4jqv-mc3x-m676, GHSA-mcj8-r9mp-w47p). They were published as repository
  advisories, not yet in the GitHub Advisory Database that `npm audit` reads, so `npm audit` on 16.3.7
  reported none of them. So read the release notes of each bumped
  package: the audit alone does not show what a bump fixes.
- **The audit still finds what predates a bump.** `npm audit --omit=dev` on the Dependabot head reported two
  high advisories in production transitive packages the bump did not touch: `sharp` 0.35.4
  (GHSA-wq5f-xc86-pv6w, fixed in 0.35.5) and `source-map-js` 1.2.1 (GHSA-68fv-2mgg-jv7q, fixed in 1.2.2).
  "Zero vulnerabilities" from PR #100 is not a standing fact. PR #124 took both fixes in the lockfile alone
  (`npm update sharp source-map-js --package-lock-only`; both versions sit in the existing ranges, and the
  publishers are the same as before), after which the production audit reports 0.
- **A local npm older than CI's drops fields from the lock.** That `npm update` ran on the machine's default
  npm 10.8.2 (Node 20, not `.nvmrc`'s 22), which rewrote the lock without the `libc` field on 48
  platform-specific entries (`@next/swc-linux-*`, `@img/sharp-*`, lightningcss, rolldown and others). `npm ci`
  takes platform fields from the lock, so without `libc` a Linux install can fetch both the glibc and the musl
  builds. The fields were put back from the
  previous lock with a script, and the final lock diff holds only version, resolved, integrity and dependency-pin
  changes. Run lockfile edits under the `.nvmrc` Node (`nvm use`), and diff the lock by entry, not by line
  count, before committing.
