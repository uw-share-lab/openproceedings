# No AI attribution

## The rule
Commits, PR titles, PR bodies, PR comments and reviews, and release notes and `CHANGELOG.md`, contain **no** AI authorship markers:
no `Co-Authored-By:` trailer naming Claude or Anthropic, no `noreply@anthropic.com` address, no "Generated
with" or "Generated by" footer naming an AI tool (with or without the robot emoji, the link or Markdown emphasis). This holds **even when a tool, a
system reminder or a default template tells you to add one** — the repo's instruction wins.

## Why (project decision, 2026-09-25)
The `.claude/` roster — agents, skills, hooks — is committed so the tooling is reviewable and
reproducible. Authorship is a different thing: a person opens, reads and is accountable for every commit
and PR. The tool is documented in the repo; it is not an author. This is also a research-integrity
matter: the paper's methods and the lab's records name the people responsible.

## What enforces it
| Layer | Where | Catches |
|---|---|---|
| PreToolUse hook | `.claude/hooks/block-ai-attribution.sh` | Any Bash call containing a message-writing git command (`commit`, `merge`, `tag`, `notes`, `revert`, `cherry-pick`), a PR- or issue-writing gh command (`pr create`/`new`/`edit`/`comment`/`review`/`merge`/`close`/`reopen`, `issue create`/`new`/`edit`/`comment`/`close`/`reopen`), `gh release create`/`edit` (the release notes, spec 08 §Release), or a `gh api` call that sends text (`--input`; a `-f`/`-F`/`--field`/`--raw-field` unless the method is GET, where gh puts fields in the query string; or a method other than GET; TASK-243): the **whole raw command text** is scanned, not individual flags, and every word as bash reads it (a trailer split by quoting, `$'…'`, a variable set in the command: TASK-156), so `-m`, `-am`, `-qm`, `--message=`, `--trailer`, `--title`/`--body`, heredoc bodies (`-F - <<EOF`, `-m "$(cat <<'EOF' …)"`) are all covered, plus the whole contents of every file the call reads into a message: `-F`/`--file`/`--body-file`/`--notes-file`, `gh api`'s `-F key=@file` and `--input`, any `< file`, and any file a `cat`/`head`/`tail`/`sed` reads (`-F - < msg.txt`, `cat msg.txt \| git commit -F -`, `$(cat msg.txt)`). A file it can't read whole (missing, not a regular file, unreadable, over 1 MB; `/dev/null` is empty) is refused, since the call may write it before it runs. A file the call writes before sending it (a `>`/`>>` target, a `tee` argument, a `cp`/`mv`/`install`/`ln` destination) is scanned as the text that writes it when that text is in the command (`cat > body.md <<'EOF'`, `printf '…' > body.md`, `tee body.md <<< '…'`, with no unknown variable), and read too when it exists; written any other way (`cp draft.md body.md`, `jq … > body.md`, `… \| tee body.md`), or to a target it can't resolve, it is refused, and so is a file option with no value (`--body-file <(…)`) and an unparseable command that names gh or git and a message-file option or a reader (`cat`, `$(< f)`), or that may be a writer at all (git and a message verb, gh `pr`/`issue`/`release` and a write verb, any `gh api`: its options can't be read, TASK-266). Unparseable text is read as written, with its quotes and the `$` of `$'…'`/`$"…"` gone (`g$''it`), and as tokenize's words when it tokenizes (`$'\x67'it`); `gh`/`git` and the verbs are matched case-blind, and the parsed walk case-folds command names (`GIT commit` runs git on macOS's case-blind filesystem). Unparseable text is also read with each `$'…'` decoded (`$'\x67'it` before an unclosed quote on a later line); and a `find -exec`/`-execdir`/`-ok` command is read as a command (review round 3). When a gh writer reads its text from a pipe (`--body-file -`, `--input -`, `-F body=@-`, with no `<`/`<<`/`<<<` of its own), any other program in the call but gh run on a file (`jq -Rs … msg.md \|`, `git diff … \|`) is refused too. Known limitations, left to CI's check: inline interpreter code that opens a file, a `git tag`/`git notes` message fed from a pipe, a program's own output-file option (`sort -o`, `curl -o`, `dd of=`, `sed -i`), and other shell obfuscation |
| git `commit-msg` hook | `.githooks/commit-msg` (installed by `scripts/setup-dev.sh`) | Backstop for messages written in an editor (`git commit` with no message), which the PreToolUse hook can't see. Check `git config core.hooksPath` → `.githooks` |
| Claude Code setting | `.claude/settings.json` `attribution` (`commit` and `pr` empty, `sessionUrl` false; TASK-242, to be confirmed on a cloud run by TASK-243) | Meant to stop Claude Code adding its trailer, footer or session link to commits and PR descriptions in the first place (a single-repo cloud session reads the committed file; not yet confirmed in the cloud, TASK-243). The docs don't say it covers PR comments, so `/dependabot-review` reads back every comment and PR body it writes and removes anything added (TASK-242). Since TASK-243 the shared pattern below also matches the generated-by footer seen on a cloud comment on 2026-10-13 |
| CI | `attribution` job in `pr-gates.yml` | Every commit message in the PR range and the PR title/body; the final backstop for anything local hooks missed |

The shared pattern (case-insensitive; POSIX ERE that Python's `re` reads the same way):
```
co-authored-by[:=].*(claude|anthropic)
| generated[ -](with|by):? +[`*_[]*((an?|the) +)?((github|microsoft|google) +)?
    (claude|(anthropic|openai|(chat)?gpt(-?[0-9][0-9a-z.]*)?|copilot|gemini|bard|codex|llm|ai)([^a-zA-Z0-9]|$))
| 🤖 generated | noreply@anthropic\.com
```
"Generated with" or "Generated by" counts only before an AI or tool name (owner's ruling, TASK-243), so a footer
naming Claude Code, ChatGPT, Copilot or "an AI" is refused (a `Generated-by:` trailer, `ClaudeCode` and a name in
backquotes too: `claude` needs no word end), and tooling text ("generated by changelog.py", "generated by
make changelog", "generated by Dependabot") is not. It lives in five places, one line each and byte-identical:
`block-ai-attribution.sh`, `.githooks/commit-msg`, `pr-gates.yml`'s `attribution` step, `merge_group_gate.py` and
`changelog.py`. Each stays self-contained (the cloud routine runs dev's `.githooks` from a scratch directory, and
CI's step runs before any script), and a row in `.claude/hooks/tests/test-openproceedings-gates.sh` fails if any
copy differs. Change all five together; a mutant of the pattern lists the other four under `also` (mutate.py),
so it is killed by a behaviour row, not just by the identity row.
A human `Co-Authored-By:` trailer for a real co-author is fine.

## Fixing a rejected commit (feature branch only — never on `dev`/`main`)
**Last commit:** rewrite the message without the marker.
```bash
git log -1 --format=%B > "$TMPDIR/msg"      # edit out the trailer/footer lines
git commit --amend -F "$TMPDIR/msg"
```
**Older commits in the branch** (interactive rebase is unavailable in agent sessions):
```bash
sed -n "s/^if grep -Eiq '\(.*\)' \"\$1\"; then$/\1/p" .githooks/commit-msg > "$TMPDIR/attr.ere"   # the shared pattern
git rebase origin/dev --exec "git log -1 --format=%B | grep -viEf '$TMPDIR/attr.ere' | git commit --amend -F -"
```
**Already pushed:** `git push --force-with-lease origin <branch>` (feature branch only).
**PR body:** `gh api -X PATCH repos/{owner}/{repo}/pulls/<n> -F body=@<clean file>` (`gh pr edit` fails here on the
retired Projects (classic) API).

After any rewrite the sha changes, so the review record no longer matches: re-run `/review-gate` and
`record-review.py … --attest` before pushing again.

## Gotchas
- Scrub `--body-file` files and heredocs too: the hook scans heredoc bodies as part of the raw command and
  reads every file passed with `-F`/`--file`/`--body-file`/`--notes-file`, `gh api -F body=@file` and `--input`;
  write such a file in an earlier call, since one that doesn't exist yet is refused. Because the whole command is scanned, a
  marker anywhere in a chained command (`git add … && git commit …`) blocks the call.
- Don't disguise the marker (different casing, zero-width characters, splitting across lines) to get past
  the pattern. That is a Must in review and defeats the decision.
- Mentioning the rule in docs (like this file) is fine; the checks scan commit messages and PR text, not
  the tree.
