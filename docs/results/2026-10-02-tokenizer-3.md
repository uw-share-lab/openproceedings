# Tokenizer 3: corpus delta and pinned replay

The controller ran the recovery harness on commit `ccd64c21` using the local Trust-Evals corpus.
[Raw results](2026-10-02-tokenizer-3.json) contain aggregate counts and replay outcomes; no query text
or abstracts are included. This is evidence for the tokenizer bump, not a claim that the later API/CLI
compatibility fixes were present in that run.

| Check                                                         | Result                                 |
| ------------------------------------------------------------- | -------------------------------------- |
| Snapshot records examined                                     | 95,877                                 |
| Records with title or abstract token changes, tokenizer 2 → 3 | 0                                      |
| Changed-token examples                                        | 0                                      |
| Tokenizer-2 pinned index                                      | `05a0541717f6`                         |
| Tokenizer-3 index of the same snapshot                        | `1fd2f5815cfb`                         |
| Historical saved queries replayed                             | 14                                     |
| Replay with each original index available                     | All `reproduced` on tokenizer 2        |
| Replay with only the new index available                      | All `drifted`, tokenizer version 2 → 3 |
| IDs added or removed in new-only replay                       | 0 for every query                      |

The replay set includes the saved Trust-Evals strings, NFC/NFD probes and source-filter probes. Zero
corpus token changes do not justify dropping the version boundary: synthetic compatibility text changes
meaning, and the version is part of the canonical hash. New-only replay correctly reports drift even
when membership happens to remain equal.

To reproduce, use a disposable scratch data directory containing copies of the original indexes,
snapshots and saved record store. Never build into the research corpus data directory. The committed
[recovery harness](2026-10-02-tokenizer-replay.py) (the controller's original, formatted) accepts four positional arguments: scratch data directory,
saved-record manifest JSON, original index version, and snapshot path. Run with the tokenizer-3 branch:

```sh
uv run python docs/results/2026-10-02-tokenizer-replay.py <scratch-data> <saved-records.json> 05a0541717f6 <snapshot-path>
```

The harness compares each title and abstract's `normalize(text, "2")` and `normalize(text, "3")`, builds
the same snapshot with tokenizer 3 using two workers, then calls `records.replay` both with and without
the old index loader. It only reads the supplied original snapshot and builds into scratch. The scratch
manifest and local research corpus are deliberately not committed.

Later recovery fixes validate pinned exports and CLI search/export/save using the selected index before
semantic refusal; source aliases and filter-edit probes use that same tokenizer. Their regression tests
build real version 2 and 3 synthetic indexes. Raw length checks remain ahead of index opening; unavailable
indexes now precede version-dependent semantic errors. API verification admission is charged once on the
target parse, including the route's base charge under the existing rate contract.

The editor now selects the highlighting lexer from `/meta.tokenizer_version`. Missing or unsupported
metadata uses tokenizer 3. A live metadata change reconfigures the CodeMirror language compartment,
retaining the document, selection and undo history. Tokenizer-2 and tokenizer-3 lexers and Lezer languages
pass independent server-generated goldens: full-width math delimiters such as `＄x OR y＄` now have the
served index's token boundaries. Diagnostics, AST, filters and membership remain server-owned.

The final tokenizer boundary is recorded in decision-033, allocated after the performance and twins decisions merged.

The schema-3 integration keeps schema and tokenizer selection independent. Fresh synthetic checks cover
all four schema 2/3 × tokenizer 2/3 combinations: membership and exact float ranking agree between schemas
for either tokenizer, and records pinned to either legacy input reproduce when the served input changes.
The focused integration run passed 227 tests; this is separate from the historical corpus measurements above.
